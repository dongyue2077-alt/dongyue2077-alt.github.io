选型的唯一标准是：**两年后我还愿不愿意为它花时间**。不是"哪个技术更先进"。

## 判断依据

一个个人博客的真实负载是：每天几十次访问、每月几篇文章、一个作者。这个负载下，任何需要常驻进程、数据库连接池、定时备份的方案，都是在用小马拉大车的方式给自己加活。

于是先列出不能接受的东西：

- 需要定期升级的运行时和依赖
- 需要备份的数据库
- 会被人扫描的登录入口
- 出故障时我修不好、只能等别人的部分

静态站把这四项全部消掉了。页面在构建时就已经是最终形态，服务器只负责把文件发出去。

## 几个被放弃的方案

**WordPress。** 功能最全，代价是要持续跟进插件和核心的安全更新。一旦停止维护，它会变成一台待被入侵的机器。

**带数据库的自建博客程序。** 多一个数据库就多一个备份策略、多一个故障点，而它带来的能力（评论、后台、草稿）对这个站点都不重要。

**在静态站上加一个后台。** 听起来两全其美，实际上是把"编辑 Markdown"换成了"维护一个会写 Markdown 的服务"，成本和风险都更高。

**全客户端渲染的前端框架。** 内容站不需要 hydration。首屏多出来的几百 KB JavaScript，换不到任何我需要的东西。

## 最终形态

构建时把 Markdown 编译成 HTML，产物是一堆静态文件。部署就是把这些文件同步到一个目录。

```bash
# 构建
npm run build

# 产物
dist/
├── index.html
├── archive/
├── posts/
│   └── hello-world/
│       └── index.html
└── rss.xml
```

这个结构还有一个额外的好处：**迁移成本几乎为零**。今天放在 GitHub Pages，明天想搬到自己的服务器，只需要换个同步目标，内容和 URL 都不用动。

## 什么时候该重新考虑

如果出现下面任一情况，说明静态站不够用了，那时再换也不迟：

- 需要登录后才能看的内容
- 需要在站内做搜索之外的服务端逻辑
- 多作者协作，且有人不愿意碰 Git

在那之前，多出来的架构都是负债。
